### API 设计

| 接口        | 方法   | 请求                     | 响应                               |
| --------- | ---- | ---------------------- | -------------------------------- |
| /register | POST | `{username, password}` | `200 OK` / `400 用户已存在`           |
| /login    | POST | `{username, password}` | `{token, playerId}` / `401 密码错误` |

### 流程

```
客户端                    登录服务器                数据库
  │                         │                       │
  │── POST /register ──────>│                       │
  │   {user, pass}          │── BCrypt.HashPassword │
  │                         │── INSERT Player ─────>│
  │<── 200 OK ──────────────│                       │
  │                         │                       │
  │── POST /login ─────────>│                       │
  │   {user, pass}          │── SELECT Player ─────>│
  │                         │<── 返回玩家记录 ──────│
  │                         │── BCrypt.Verify        │
  │                         │── 生成 JWT Token       │
  │<── {token, playerId} ───│                       │
```

### 关键知识点

- **BCrypt**：密码哈希算法，不可逆。即使数据库泄漏，攻击者也无法还原密码
- **JWT Token**：无状态认证。服务器不存 Session，Token 自带玩家信息 + 过期时间 + 签名
- **Dapper**：轻量 ORM。`db.QueryAsync<T>("SELECT ...")` 直接映射成 C# 对象

### 参考代码

```csharp
// Program.cs (ASP.NET Core Minimal API)
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<DbHelper>();
var app = builder.Build();

app.MapPost("/register", async (Player req, DbHelper db) =>
{
    var existing = await db.QueryFirstOrDefaultAsync<PlayerData>(
        "SELECT * FROM Player WHERE Username = @u", new { u = req.Username });
    if (existing != null)
        return Results.BadRequest("用户已存在");

    var hash = BCrypt.Net.BCrypt.HashPassword(req.Password);
    await db.ExecuteAsync(
        "INSERT INTO Player (Username, PasswordHash) VALUES (@u, @p)",
        new { u = req.Username, p = hash });
    return Results.Ok();
});

app.MapPost("/login", async (Player req, DbHelper db) =>
{
    var player = await db.QueryFirstOrDefaultAsync<PlayerData>(
        "SELECT * FROM Player WHERE Username = @u", new { u = req.Username });

    if (player == null || !BCrypt.Net.BCrypt.Verify(req.Password, player.PasswordHash))
        return Results.Unauthorized();

    var token = JwtHelper.GenerateToken(player.Id, player.Username);
    return Results.Ok(new { token, playerId = player.Id });
});

app.Run();
```

### 消息协议

```csharp
public enum MsgType : byte
{
    C2S_Login = 1,        // 登录（带 Token）
    S2C_LoginAck = 2,     // 登录回复
    C2S_Heartbeat = 3,    // 心跳
    S2C_HeartbeatAck = 4, // 心跳回复
    C2S_Input = 5,        // 玩家操作
```

## 阶段 4：protobuf 通信

**目标**：前后端通信统一使用 protobuf（.proto 文件定义协议），覆盖 UDP 实时通信和 HTTP 通信

**学习技能**：Google.Protobuf + Grpc.Tools + .proto 协议设计 + IL2CPP AOT 兼容

### 为什么用 proto

- 前后端共用一份 .proto，改协议只改一处，避免手工同步两套序列化代码
- 二进制序列化，比 JSON 更省带宽和 CPU
- 强类型，编译期检查字段，比手写字节序更安全

### 任务清单

- [x] GameServer 引入 Google.Protobuf + Grpc.Tools，最小 .proto 生成 C# 代码跑通
- [x] 客户端 Unity 引入 Google.Protobuf（IL2CPP AOT 兼容处理）
- [x] 定义公共 .proto（UDP 战斗/推送消息 + 信封）
- [x] UDP 消息改为 proto 序列化（替换手动 NetDataWriter 写法）
- [x] HTTP 消息改为 proto（登录/养成请求响应，替换 JSON）
- [x] 前后端 proto 联调验证

### 最终架构决策

- **HTTP 和 UDP 都用 proto**：登录/养成数据（HTTP）与帧同步/推送（UDP）统一使用 proto，前后端共用一份 .proto
- **HTTP 传输方式**：Content-Type: application/x-protobuf，请求体/响应体直接发 proto 二进制
- **UDP 信封模式**：NetMsgEnvelope（msg\_type + payload），新增消息只加 type 常量 + case 分支
- **传输/协议分层**：Framework/NetMgr 只做传输（byte\[] 收发），Game/NetMsgHandler 做协议解析（热更层，新增协议只需热更）
- **错误码**：用 ErrorCode 枚举而非字符串 error；`error_code` 固定放 field 1，业务字段从 field 2 往后排，新增字段直接往下追加

### HTTP 接口注册与 URL 共享约定（阶段 4 补充）

HTTP API 的 URL 两端共享，且 ApiRegistry 由工具自动补全，遵循以下约定：

**URL 共享**：`Server/wgame-server/Proto/NetApi.cs`（手写共享常量）

- 服务器 LoginServer.csproj 用 `<Compile Include>` 链接引用
- 客户端由 gen\_proto.sh 复制到 `Game/Net/Proto/`

**字段命名约束**：字段名必须与 proto 类型名语义一致

- 字段名 `X` + 注释 `// POST` → 自动注册为 `RegisterPost<NetMsg.XReq>`
- 字段名 `X` + 注释 `// GET` → 自动注册为 `RegisterGet<NetMsg.XResp>`
- 例：`GetMe` 对应 `GetMeResp`（不能写成 `Me`）

**注释里的方法标识不区分大小写**（post/get/POST/GET 均可）

**自动补全**：Unity ToolBox "导 Proto" 成功后调用 `AutoCompleteApiRegistry`（ToolBox.Excel.cs）

- 解析 NetApi.cs 生成 ApiRegistry.RegisterAll 方法体并写回
- 新增接口流程：NetApi.cs 加一行 `public const string Xxx = "/xxx";   // POST` → 点导 Proto → 自动补全

**业务层调用**（无需写 URL）：

```csharp
// POST：请求类型自动查表
GameMgr.HttpMsg.Post<NetMsg.LoginResp>(req, resp => {...});
// GET：响应类型自动查表
GameMgr.HttpMsg.Get<NetMsg.GetMeResp>(resp => {...});
```

### 命名规范

| 结构 | 方向              | 后缀     | 示例          |
| -- | --------------- | ------ | ----------- |
| 请求 | 客户端 → 服务器       | `Req`  | `LoginReq`  |
| 响应 | 服务器 → 客户端（跟随请求） | `Resp` | `LoginResp` |
| 推送 | 服务器 → 客户端（主动）   | `Push` | `MailPush`  |

- 请求与响应必然成对：`XxxReq` ↔ `XxxResp`（同功能名）
- 推送独立，无请求对应

### 注意事项

- 生成代码在 obj/ 下（服务器）和 Assets/Scripts/Game/Net/ 下（客户端），**不要手动改**，.proto 才是协议定义源；改协议后两端重新生成
- 服务器 Grpc.Tools 在 build 时自动生成；客户端需跑 DataTables/gen\_proto.sh（或 Unity ToolBox 导 Proto 按钮）
- Unity 是 HybridCLR + IL2CPP，Google.Protobuf 默认反射式序列化有 AOT 兼容问题，需 link.xml 保留类型
- **错误码约定**：所有 Resp 的 error\_code 用 ErrorCode 枚举，固定放 field 1，业务字段从 field 2 往后排；字段顺序不影响序列化（由字段号标识），调整仅为可读性
- **传输/协议分层**（关键架构）：NetMgr（Framework/AOT）只做 byte\[] 传输不依赖协议；NetMsgHandler（Game/热更）做协议解析 -- 因为 Framework 不能引用 Game（依赖方向单向）

### 实现记录（2026-08-18）

**协议变更**（net_battle.proto）：

- `PlayerInput.param3`（字段 4，笔误）修正为 `param2`（字段 3），新增 `player_id`（字段 5）
- `player_id` 由服务器广播时填充（取连接标识 peer.Id），客户端无法伪造身份；阶段 6 JWT 校验后替换为 token 解析的 playerId

**服务器**（GameServer/Program.cs）：

- 主循环：固定步长累加器模式（业内通用，Fix Your Timestep）：`PollEvents` + Stopwatch 单调时钟累积时间，每满 50ms 消费一帧把 `_pendingInputs` 打包成 `FrameData` 广播；卡顿后最多补 3 帧（死亡螺旋保护）；睡眠按"距下一帧边界"分片（单片 ≤5ms），不忙等（阶段 5 无房间概念，全体在线客户端视为同一场游戏）
- 空帧也广播（每秒 20 帧、每帧十几字节，开销可忽略），客户端按连续帧号驱动，无需处理跳帧
- 操作校验：op_type 超范围丢弃；单帧每玩家操作数 > 8 视为刷包丢弃
- 日志：空帧不打印避免刷屏

**客户端**（热更层）：

- `NetMsgHandler`：新增 `MsgFrameData` 分支 + `OnFrameData` 事件，协议层不依赖业务
- `FrameSyncMgr`（新增，Game/Net）：`SendInput` 发操作；收帧入队列；`MyUpdate` 累积时间每 50ms 消费一帧；缓冲 < 2 帧暂停消费且计时钳制一帧的量（恢复后立即消费不快进）；帧号跳变告警；断线清空状态；Priority=90 在 NetMgr(100) 之后轮询
- 业务层订阅 `FrameSyncMgr.OnFrame` 驱动确定性逻辑（inputs 顺序在所有客户端一致）

**验证方式**：启动 GameServer（dotnet run），Unity 两个实例：TTTT 组件右键"执行"连接 -> "订阅帧日志" -> 各自"发送操作"，双端日志应看到帧号连续、且能收到对方 playerId 的操作

### 实现记录：确定性改造（2026-08-18 第二批）

**架构分层**（关键：模拟层与表现层彻底分离）：

- `BattleSim`（Game/Battle/TD/）：纯 C# 确定性模拟层，不引用 UnityEngine。输入 = 帧号 + 操作列表，输出 = 实体状态 + 状态哈希
- `BattleTD`（表现层）：订阅 FrameSyncMgr.OnFrame 喂给模拟层，用运行时图元（方块/圆柱）做视图同步；表现层可以随意用 float/插值/特效，不影响确定性
- 定时锚点：模拟层以服务器绝对帧号驱动（Tick(absFrame)），后进场客户端用空帧快进对齐（前提：进场前无人操作，阶段 6 由 StartGame 消息统一进场帧根治）

**确定性数学**（FixMath.cs）：

- `Fix` Q16.16 定点数：64 位整数存储（高 48 位整数 + 低 16 位小数），精度 1/65536、范围 ±32767，纯整数运算跨平台一致；含 Sqrt（整数位扫描法）。逻辑层禁用 float/double
- `XRng`：xorshift64* 确定性随机，同种子序列跨平台一致；战斗逻辑禁用 UnityEngine.Random / System.Random。种子暂为常量，阶段 6 由 StartGame 下发

**规则与约束**（BattleSim）：

- 操作：1=放塔(格子坐标，100 金币起，占格/越界/金币不足拒绝) 2=升级塔(30 金币，仅塔主人，3 级上限)
- 刷怪按绝对帧号调度（每 60 帧一波，数量/血量只由帧号决定），敌人沿固定路径点匀速移动（0.07 格/帧）
- 塔攻击选"距离最近的敌人"（并列取先刷出的），距离用平方比较避免 Sqrt；击杀奖励进塔主人金币
- 遍历顺序固定：实体用 List 按索引遍历，玩家按首次操作顺序排列；禁用 Dictionary 遍历
- `StateHash()`：FNV-1a 哈希全量状态（帧号/金币/实体位置 raw 值等），双端逐帧对比即可验证确定性

### 实现记录：定点数与随机数易用 API（2026-08-19）

**问题**：业务侧用 `Fix.FromRaw(4587)` 这种魔法数可读性差；`XRng.NextInt(min,max)` 覆盖不了"随机小数/概率判定"等常见需求。

**改动**（FixMath.cs）：

- `Fix.FromDouble(v)`：业务常量直接写小数（`Fix.FromDouble(0.07)`），内部四舍五入转 raw。**确定性依据**：字面量编译期位模式唯一（ECMA-335）+ IEEE754 运算规范，仅限初始化常量场景，禁止逐帧逻辑用浮点动态构造。整数优先 `FromInt(3)`
- Fix 范围更正：64 位存储 = 48 位整数 + 16 位小数，**±1.4e14**（旧注释误写 ±32767）
- BattleSim 魔法数替换：`FromRaw(4587)→FromDouble(0.07)`、`FromRaw(196608)→FromDouble(3.0)`（raw 值不变，哈希不受影响）
- XRng 新接口（全部基于 NextULong 纯整数链，双端一致）：
  - `NextInt(max)`：[0,max) 简写
  - `NextFix(min, max)`：[min,max) 均匀随机 Fix，直接写业务小数如 `rng.NextFix(0.1, 0.3)`
  - `Chance(pct)`：百分数概率判定（pct=5 即 5%），内部万分比整数比较
  - `ChanceBp(bp)`：万分比概率判定（bp=500 即 5.00%），配置表字段直传

**验证**：独立控制台跑 4000 次混合调用双实例同种子序列逐值一致；Chance(5) 十万次命中 5.039%；NextFix(0.1,0.3) 范围正确；边界 0%/100% 行为正确

**帧同步配置纪律**（讨论结论）：Luban float 字段（如 interval=0.2）在本项目链路（.NET 双端 + bytes 同文件）下确定可用，取出即转 Fix、勿用 float 做中转运算；进模拟层的数值字段建议 int + 单位语义（毫秒/帧/万分比）更稳妥，纯表现层字段 float 无妨

### 实现记录：真机联调适配（2026-08-19）

Editor + 真机双端哈希逐帧一致，**阶段 5 验证通过**。真机暴露两个表现层问题（均不影响确定性）：

**1. 图元全粉色**：`CreatePrimitive` 默认材质是 Built-in Standard shader，URP 真机不渲染（Editor 有兜底）；且 URP Lit 颜色属性是 `_BaseColor`，`Material.color`（写 `_Color`）无效。修复：BattleTD 材质工厂 `GetMat/SetMat`。**注意**：真机上项目材质全在 Addressables bundle，URP Lit shader 只进 bundle 不进主包，`Shader.Find` 主包阶段返回 null（直接 new Material 会抛 ArgumentNullException）--兜底链：Shader.Find URP Lit/Unlit -> **克隆 `GraphicsSettings.currentRenderPipeline.defaultMaterial`**（管线初始化必备，真机必在）-> Sprites/Default。SetColor 同时写 `_BaseColor`/`_Color` 兼容各 shader，按颜色静态缓存 + sharedMaterial 赋值避免实例泄漏

**2. `Can't add component because class 'BoxCollider' doesn't exist`**：HybridCLR + IL2CPP 裁剪问题。`CreatePrimitive` 在 native 内部按类名加 BoxCollider，C# 侧无显式引用，HybridCLR 生成的 link.xml（Assets/HybridCLRGenerate/link.xml）扫描不到 -> PhysicsModule 只保留了 Collider 基类，BoxCollider 被裁。修复：新建独立的 `Assets/link.xml`（不会被 HybridCLR 重新生成覆盖，Unity 自动合并所有 link.xml）：`<assembly fullname="UnityEngine.PhysicsModule" preserve="all" />`

**3. 真机场景加载规则**（HybridCLR 限制）：热更脚本只能挂在 Addressables/AB 打包的场景或预制体上（加载时机在热更 DLL 之后）；**Build Settings 主包场景绝对不能挂热更脚本**（打包时引用就断，真机报 referenced script missing + serialization layout 不匹配）。真机测试方案：TTTT 挂 Main 场景（Addressables）+ `GameMgr.IsInited` 防重复初始化（真机流程 StartGame 已 Init，TTTT.Start 只在 Editor 直 Play 测试场景时补 Init）；Editor 继续直 Play Test 场景的习惯不变
